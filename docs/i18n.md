# Localization

Synara's source language is English. This fork adds other display languages **without editing the
component source**, so upstream merges stay conflict-free.

## Why it works this way

The obvious approach — `react-i18next` or similar — replaces every literal in the UI with a `t("key")`
call. In this codebase that touches roughly 250 files and every one of them is a file upstream also
edits. Each upstream merge would then conflict on the same lines, forever.

So the translation happens one layer lower, at the compile boundary:

- A Babel plugin (`packages/i18n/src/babelPlugin.ts`) rewrites user-facing string literals into
  `t("<English source>")` while the web app is bundled.
- The catalogue is keyed by the **English source text**, not by invented ids.
- Anything not in the catalogue falls through to its English source.

The working tree therefore stays byte-identical to upstream, apart from the wiring listed below.

| Property                             | `t("key")` in components | This transform       |
| ------------------------------------ | ------------------------ | -------------------- |
| Upstream files modified              | ~250                     | 4                    |
| New upstream string behaves as       | (no code, no string)     | renders in English   |
| Merge conflicts per upstream release | many                     | only if the 4 change |
| Translator sees                      | `settings.theme.title`   | `Theme`              |

## What is wired into the app

Everything else is new files under `packages/i18n/`.

| File                                     | Change                                              |
| ---------------------------------------- | --------------------------------------------------- |
| `apps/web/vite.config.ts`                | registers the plugin inside the existing babel pass |
| `apps/web/src/main.tsx`                  | awaits `initLocale()` before the first render       |
| `apps/web/package.json`                  | `@synara/i18n` workspace dependency                 |
| `apps/web/src/routes/_chat.settings.tsx` | renders `<LanguageSettingsPanel />`                 |
| `apps/web/src/settingsNavigation.ts`     | anchor-id fallback (see _Hazards_)                  |

`SYNARA_I18N=off bun run build` compiles the untranslated upstream bundle, which is the quickest way
to tell whether a bug is yours or upstream's.

## What gets translated

The rules live in one place, `packages/i18n/src/policy.ts`, shared by the transform and the
extractor so the keys they produce can never drift.

- **JSX text.** `<p>Save changes</p>`. Whitespace is normalized the way React renders it, so
  a string split across source lines becomes one key, and a significant edge space stays outside it.
- **Allowlisted JSX attributes**: `aria-label`, `placeholder`, `title`, `alt`, `label`,
  `description`, and a few more.
- **Allowlisted object properties**: `label:`, `description:`, `title:`, `eyebrow:` … Most of
  Synara's copy lives in `as const` option tables rather than in JSX, so this is the largest source.
- **Hand-written `t("…")` calls.** Import `t` from `@synara/i18n/runtime` anywhere you need it —
  including for strings that arrive at runtime, since lookup is by English text.

Never translated: `className`, `value`, `id`, `key`, `icon`, anything that looks like a class list,
URI, or dotted/kebab identifier.

## Opting out

```tsx
// i18n-ignore
const MODES = { label: "Compact" }; // stays English

// i18n-ignore-file  (as the first comment in the file)
```

## Catalogue files

Each locale has three files under `packages/i18n/locales/`, all generated and reconciled by
`bun run i18n:extract --sync`:

| File                | Contents                             | Ships in the bundle |
| ------------------- | ------------------------------------ | ------------------- |
| `<id>.json`         | finished translations only           | yes                 |
| `<id>.todo.json`    | keys still awaiting translation      | no                  |
| `<id>.retired.json` | translations upstream no longer uses | no                  |

This split, and the `--sync` reconciliation that maintains it, is GNU gettext's model:
`_catalogue.json` is the `.pot`, `<id>.json` is the `.po`, and `--sync` is `msgmerge`. The
catalogue is keyed on the English source exactly as gettext keys on `msgid`, which is why a
missing entry degrades to correct English instead of to a visible key.

Splitting them keeps dead weight out of the download: only real translations ship, so the chunk
carries no empty placeholders. `_catalogue.json` (every extractable string, mapped to the files it
came from) and `_uncovered.json` (the coverage gap) are shared across locales.

Each catalogue is a separate bundle chunk, so a session downloads only the language it uses, and an
English session downloads none.

## What is deliberately left in English

Not every extracted string should be translated, and `<id>.todo.json` is where that judgment gets
recorded — an empty value means "reviewed, stays English" just as much as "not done yet".

- **Proper names**: theme names (Tokyo Night, Gruvbox, Catppuccin), integration names (Linear,
  Notion, Sentry), provider and model names.
- **Command and binary names** that a user types or that address a file: `codex`, `claude`,
  `devin auth login`, `CODEX_HOME`, `npm run dev`.
- **Release history.** `whatsNew/entries.ts` is excluded from extraction entirely — see
  `EXCLUDED_CONTENT_PATTERN` in `policy.ts` for why.

Anything short and ambiguous (`Fast`, `Make`, `One`, `UI`) needs someone to look at where it
renders before deciding; the catalogue's file provenance is there to make that quick.

## Locale identifiers

Ids are **script-based** BCP 47 tags — `zh-Hans`, not `zh-CN`.

`zh-CN` is a legal tag, but it names a country and only implies Simplified by convention. CLDR
expands it to `zh-Hans-CN`; Simplified is equally the script of `zh-SG` and `zh-MY`, while `zh-HK`
and `zh-MO` are Traditional. Keying a catalogue on the script says what the file actually contains,
and leaves `zh-Hant-TW` and `zh-Hant-HK` free as separate entries instead of colliding with a
region-named id.

Matching does not use a hand-maintained prefix table. `matchLocale` expands both the requested tag
and each shipped id with `Intl.Locale#maximize()`, then compares language and script, using region
only as a tiebreaker:

| Platform reports       | Resolves to | Why                                       |
| ---------------------- | ----------- | ----------------------------------------- |
| `zh-CN`, `zh`, `zh-SG` | `zh-Hans`   | all expand to the Hans script             |
| `zh-TW`, `zh-HK`       | `en`        | Hant has no catalogue; see below          |
| `en-GB`                | `en`        | language and script match, region differs |

Script equality is **required**: serving Simplified copy to a Traditional reader reads as a bug, so
English is the honest fallback until a Hant catalogue exists. Adding one is two lines here plus the
translations — but do not machine-convert Simplified to Traditional, because the mapping is
one-to-many (发/髮, 后/後, 干/乾/幹) and silently produces wrong words.

A preference stored under an id that is no longer shipped is re-resolved through the same matcher
rather than discarded, so an older `zh-CN` value keeps selecting Simplified Chinese.

### Which parts are standards, and which are ours

Almost all of it is standard. The tags are BCP 47 (RFC 5646 for syntax, RFC 4647 for matching),
whose subtags come from ISO 639 (language), ISO 15924 (script) and ISO 3166-1 / UN M.49 (region),
assembled in the IANA Language Subtag Registry. The data behind them is Unicode CLDR, and the
algorithms are UTS #35 (LDML). We reach all of that through ECMA-402: `Intl.Locale#maximize()` _is_
CLDR "Add Likely Subtags", and `Intl.DisplayNames` _is_ CLDR display names. Alias canonicalization
comes along for free — `iw`→`he`, `in`→`id`, `sh`→`sr-Latn`, `cmn`→`zh-Hans`, `tl`→`fil`.

The one piece ECMA-402 does not expose is a general-purpose matcher: `localeMatcher` is internal to
the `Intl` constructors. `Intl.LocaleMatcher` is a TC39 **Stage 1** proposal, ponyfilled by
`@formatjs/intl-localematcher`. Measured against `["en", "zh-Hans"]`:

| Requested | RFC 4647 `lookup` | ECMA-402 `best fit` | Ours      |
| --------- | ----------------- | ------------------- | --------- |
| `zh-CN`   | `en`              | `zh-Hans`           | `zh-Hans` |
| `zh-TW`   | `en`              | `zh-Hans`           | `en`      |
| `zh-Hant` | `en`              | `zh-Hans`           | `en`      |
| malformed | throws            | throws              | `en`      |

Neither built-in algorithm is what this app wants. `lookup` truncates `zh-CN` to `zh`, finds no
`zh` catalogue, and misses Simplified entirely. `best fit` crosses scripts, handing Traditional
readers — including someone who explicitly asked for `zh-Hant` — Simplified copy. Both throw on the
malformed tags that platform language lists occasionally carry, which would fail at boot.

So the ~15 lines in `locales.ts` are not a reimplementation of the standard; they are likely-subtags
expansion (standard) plus one product decision (require script equality) that neither built-in
algorithm encodes. If the app ever ships many locales, `best fit` plus a script guard is the
upgrade path — but adding the dependency today buys nothing.

## Adding a language

1. Add an entry to `LOCALES` in `packages/i18n/src/locales.ts`.
2. Add its loader to `CATALOGUE_LOADERS` in `packages/i18n/src/runtime.ts`.
3. `bun run i18n:extract --sync` creates the three files above; every key starts in `.todo.json`.
4. Fill in values in `.todo.json`, then run `--sync` again — filled entries graduate into the
   shipped catalogue and the rest stay on the work list.

## After merging upstream

```bash
git fetch upstream && git merge upstream/main
bun run i18n:extract --sync     # refresh the catalogue
git diff packages/i18n/locales  # exactly the copy upstream added or changed
```

New keys land in `<id>.todo.json` and render in English until translated. Keys upstream removed move
to `<id>.retired.json` rather than being deleted, so a reverted upstream change brings the
translation straight back.

`bun run i18n:extract --check` exits non-zero when the catalogue is stale — worth adding to CI.

### Reading the drift report

`--sync` reports what changed since the last run, which is how a scanning approach stays honest:

```
[i18n] since last sync: +2 new, -3 no longer extracted
[i18n]   gone from apps/web/src/components/Sidebar.tsx: "A label upstream no longer exposes"
[i18n]   2 of the new strings look like rewordings:
[i18n]     was: "Display language now"
[i18n]     now: "Display language"
```

A string that stops being extracted is the one failure mode this approach has and a hand-written
`t(...)` call does not: upstream moves copy into a shape `policy.ts` does not cover, and coverage
drops with nothing failing. Naming the file it left makes that diagnosable. The rewording pairs are
`msgmerge`'s fuzzy matching, minus the auto-apply — reworded copy usually needs a reworded
translation, so the old value waits in `<id>.retired.json` for a human rather than being reused.

The catalogue records **which files** a string came from, never a line or a character offset. That
is deliberate: line-anchored records are what a patch series carries, and they are what breaks when
upstream edits _near_ a string rather than the string itself. File paths survive that and still
answer the only question worth asking after a merge — "what changed here?"

## Coverage gaps

`packages/i18n/locales/_uncovered.json` lists every interpolated string the transform cannot key on
(`` `Loading ${kind} diff...` ``). These stay English. Fixing one means restructuring the call site,
which _is_ an upstream-file edit, so only do it where it matters.

Two other surfaces are out of scope today and would each need their own pass:

- **Electron native menus** (`apps/desktop/src/main.ts`) — a separate process, built without Babel.
- **Server-generated messages** (`apps/server`) — these arrive as data. They can be translated at
  the display site with `t(message)`, because catalogue lookup is by English text; the catalogue
  entry has to be added by hand or via a `t("…")` call the extractor can see.

## Hazards

A display string that also acts as an identifier breaks when translated. Two defences:

**The transform refuses a string the same file also uses as a value.** Before rewriting anything it
collects every string literal the file compares with `===`, switches on, uses as a computed key,
passes to `.has()`/`.get()`/`.includes()`, or names in a type position — and leaves those in the
source language. This is not hypothetical: `Sidebar.logic.ts` produces `label: "Completed"` and
elsewhere asks `status.label === "Completed"`. Translating only the first inverts the comparison,
and no test written in English would catch it.

The cost is real: 18 status labels (`Working`, `Completed`, `PR merged`, `Plan Ready`, …) are
discriminants across several files, so they stay English. Correctness beats coverage here. To
recover one, translate it at the display site with `t(status.label)` — lookup is by English text, so
it works on a runtime value — but that edits an upstream file, so weigh it against the merge cost.
The guard is per-file, so the same string used purely as copy elsewhere still translates.

**`settingRowAnchorId()` falls back to a hash.** It slugs a settings row title into a DOM id, and a
Chinese title slugs to the empty string, which would give every row in a section the same id.

If you add an allowlisted property name, look for the same pattern before trusting it.

## Changing language at runtime

Changing the language reloads the app. Translated literals are read during render and cached by the
React Compiler and by `useMemo`, and a locale change does not invalidate those caches, so a live
swap would leave stale copy on screen. This is the same contract desktop editors use for display
language.
